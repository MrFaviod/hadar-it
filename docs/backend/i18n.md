# Internationalization (core, registry and language packs)

The core layer ships two catalogs (`es`, `en`); every other language, extension
translation and localized doc comes from the versioned catalog registry. Plural
rules, time zones and currency data come from [Babel](https://babel.pocoo.org/).

## Messages

Core catalogs live in `itsm/i18n/catalogs/{es,en}.json` as a flat map of dotted
keys (`api.*` for product text). `itsm/i18n/catalogs/context.json` records, per
key, where and how the text is used; every catalog key must have an entry, and
both catalogs must define the same keys with the same parameter names
(`tests/test_i18n_catalog.py`).

Namespace ownership:

- `ui.*` — the frontend registers its source catalog through
  `PUT /api/v1/i18n/sources/ui`.
- `api.*` — the backend core catalogs.
- `ext.<extensionId>.*` — the module with that id, and only that id. A module
  that defines another namespace, or repeats a key it does not own, fails
  admission.

Message syntax:

- Named parameters: `"El idioma {locale} no está instalado."`
- Plural forms separated by ` | ` in CLDR category order for the locale, chosen
  by `babel.Locale.plural_form(count)` from the `count` parameter.

`t(key, locale, **params)` never returns a raw key: a missing key logs one
warning and renders the localized `api.i18n.text_unavailable` text.

## Precedence

For one `(locale, key)` the resolved text is the first match of:

1. a custom translation stored for that locale and key;
2. a language pack `override` (higher `priority` first, then lexicographically
   greater pack id);
3. the namespace owner catalog (core or the module that owns `ext.<id>.*`);
4. a non-overriding pack that fills the gap (same priority/id order).

Locale resolution falls back through the parent chain (`pt-BR` → `pt`), then the
installation `defaultLocale`, then `es`. `GET /api/v1/i18n/bundle` reports that
chain in `fallback` instead of duplicating the default catalog in `messages`.

The request locale is the authenticated user's own `locale` preference, then
`Accept-Language` negotiated against installed tags, then the installation
default. Locale, time zone and currency are independent settings.

A stored preference is never rewritten. If the pack that installed it is
uninstalled, the effective locale becomes the first installed tag of the
preference chain (parent, then installation default) and the preference stays
stored so reinstalling the pack restores it.
`itsm/i18n/registry.effective_locale` is the single resolution used by the
session envelope, request-locale negotiation, localized error messages,
documents and notification recipients; `/auth/login` and `/auth/me` report the
effective `locale` next to `preferences.locale`, which remains the stored tag.

## Registry

`itsm/i18n/models.py` stores providers, locales, entries and docs in main SQL;
`itsm/i18n/registry.py` is the only reader/writer and keeps a monotonic
`revision`. Every install, update, review, uninstall or custom translation
bumps the revision, and the bundle `ETag` is derived from it, so a cached
response can never outlive a translation change.

An installed draft language pack stays inactive: it is listed only after an
authorized user reviews it as `reviewed`. Uninstalling a pack deletes its rows;
the earlier owner/other-pack translations come back because the snapshot is
recomputed and owner catalogs are never modified.

## Endpoints

| Method | Path | Access | Purpose |
|---|---|---|---|
| `GET` | `/api/v1/i18n/locales` | public | installed locales (with provider), `defaultLocale`, installation `timezone`/`currency`, revision |
| `GET` | `/api/v1/i18n/bundle?locale=pt-BR` | public | resolved `messages`, `overrides`, `fallback` chain and revision; `ETag` + `If-None-Match` → `304`; unknown locale → `404` |
| `GET` | `/api/v1/i18n/docs?locale=pt-BR&topic=licenses` | authenticated | one localized doc topic from an installed, reviewed pack |
| `PATCH` | `/api/v1/auth/me/preferences` | cookie session + Origin/CSRF | the caller's own `locale`; `null` follows the installation; unknown tag → `422` |
| `PUT` | `/api/v1/i18n/settings` | `system.configure` | installation `defaultLocale`, `timezone`, `currency` |

The public endpoints require no session; in demo mode they stay public and are
subject to the same release-mode rules as every other route. The session
envelope (`/auth/login`, `/auth/me`, preference updates) adds `locale`,
`preferences` and `installation` next to the existing fields.

Installation values are validated with Babel: an IANA time zone
(`babel.dates.get_timezone`) and an ISO 4217 currency
(`babel.core.get_global("all_currencies")`). A rejected request stores nothing.

## Translator tools

The translator page is built on a second, additive endpoint set under
`/api/v1/i18n`. All of them are authenticated: **reads require `system.view`**,
**writes require `system.configure`**, and a cookie write keeps the Origin and
CSRF guards of every other mutation (a missing/forged pair is `403`
`api.auth.csrf_invalid`, a missing permission is `403`
`api.identity.permission_denied`). Every successful write bumps the registry
revision, so every cached bundle `ETag` changes. A rejected write stores nothing
and leaves the revision untouched.

| Method | Path | Access | Purpose |
|---|---|---|---|
| `PUT` | `/api/v1/i18n/sources/ui` | `system.configure` | register the frontend `ui.*` source catalog (idempotent by content hash) |
| `GET` | `/api/v1/i18n/coverage` | `system.view` | per installed locale: totals, missing keys (paged, with context) and which provider supplies each locale |
| `GET` | `/api/v1/i18n/export` | `system.view` | download one locale (optionally one namespace) as JSON or gettext PO |
| `POST` | `/api/v1/i18n/import` | `system.configure` | validate and store a catalog in the locale's **custom** layer |
| `POST` | `/api/v1/i18n/validate` | `system.view` | the same report as import, without writing |
| `DELETE` | `/api/v1/i18n/custom/{locale}/{key}` | `system.configure` | delete one custom translation |
| `DELETE` | `/api/v1/i18n/custom/{locale}` | `system.configure` | reset the whole custom layer of a locale |

### Source: `PUT /i18n/sources/ui`

The frontend ships its own `ui.*` catalog, so the backend cannot know those keys
until they are registered. The registration is a **source** provider: it feeds
coverage, validation and export, and it is never overlaid on the resolved
messages (the browser already merged its built-in catalog). Only `ui.*` keys are
accepted; `api.*`, `ext.*` and malformed keys are rejected.

```json
{
  "catalogs": {
    "es": {"ui.dashboard.title": "Panel", "ui.dashboard.count": "{count} activo | {count} activos"},
    "en": {"ui.dashboard.title": "Dashboard", "ui.dashboard.count": "{count} active | {count} active items"}
  },
  "context": {
    "ui.dashboard.title": "Dashboard page heading.",
    "ui.dashboard.count": "Asset count badge in the dashboard cards."
  }
}
```

The Spanish (`es`) catalog is mandatory: it is the source text every other
locale is validated against. The response is
`{"source": "ui", "changed": true, "digest": "<sha256>", "revision": 3, "locales": ["es", "en"], "keys": 2}`.
Re-registering identical content returns `changed: false`, keeps the revision
and therefore does not invalidate any cached bundle. Rejected content returns
`422` `api.i18n.source_invalid` with `report.problems` (see below).

### Coverage: `GET /i18n/coverage`

Query parameters: `locale` (optional, must be installed; unknown → `404`
`api.i18n.unknown_locale`), `namespace` (optional prefix such as `api`, `ui` or
`ext.acme`; invalid → `422` `api.i18n.invalid_namespace`), `limit`
(1–500, default 50) and `offset` (default 0). The **source** is Spanish and
contains the `api.*` catalog, the registered `ui.*` text and the `ext.<id>.*`
entries owned by installed extensions.

```json
{
  "revision": 7,
  "sourceLocale": "es",
  "namespace": null,
  "page": {"limit": 50, "offset": 0},
  "source": {"locale": "es", "total": 1147, "namespaces": {"api": 1144, "ui": 3}},
  "locales": [
    {
      "tag": "pt-br",
      "displayTag": "pt-BR",
      "name": "Portuguese (Brazil)",
      "nativeName": "Português (Brasil)",
      "localeProvider": "pt-br-pack",
      "source": false,
      "total": 1147,
      "translated": 42,
      "percentage": 3.66,
      "providers": [
        {"id": "pt-br-pack", "kind": "language-pack", "entries": 42},
        {"id": "custom", "kind": "custom", "entries": 2}
      ],
      "custom": {"entries": 2, "orphaned": []},
      "missing": {
        "total": 1105,
        "limit": 50,
        "offset": 0,
        "items": [{"key": "api.assets.created", "context": "Asset created successfully."}]
      }
    }
  ]
}
```

`tag` is the canonical (lower-case) tag the other endpoints accept;
`displayTag` is the installed spelling. `percentage` counts translated source
keys only (`round(translated * 100 / total, 2)`, `100.0` for an empty source) and
`missing.items` is sorted by key and carries the shipped or registered context.
`localeProvider` is `core`, an extension id or a language-pack id, and
`providers` lists every provider that supplies text for the locale (`core`,
`ui-source`, `extension`, `language-pack`, `custom`). The `custom.orphaned` list
reports stored custom keys that a core update removed (see below).

### Export: `GET /i18n/export`

Query parameters: `locale` (required, installed), `format` (`json` default, or
`po`; anything else → `422` `api.i18n.unsupported_format`) and `namespace`
(optional prefix). Both formats download with
`Content-Disposition: attachment; filename="<locale>[.<namespace>].<ext>"` and
only include source keys that already have a text in that locale.

- `json` → `application/json`, a flat `{key: text}` object.
- `po` → `text/x-gettext-translation`, one entry per key with
  `msgctxt = key`, `msgid = Spanish source text`, `msgstr = translation` and the
  context as a `#.` automatic comment. Babel's `babel.messages.pofile` writes and
  reads it, so Poedit/Weblate round-trip works.

### Import and validate

`POST /i18n/import` and `POST /i18n/validate` share one body; both return the
same report. The difference is that import stores the valid entries in the
**custom** layer (highest precedence) and bumps the revision, while validate
only reports and stores nothing.

```json
{"locale": "pt-BR", "format": "json", "content": "{\"api.error.not_found\": \"Não encontrado.\"}", "dryRun": false}
```

`format` is `json` or `po`; `content` is the catalog text itself. `dryRun: true`
(import only) validates without writing. The report:

```json
{
  "locale": "pt-br",
  "format": "json",
  "valid": false,
  "dryRun": false,
  "entries": 2,
  "applied": 0,
  "revision": 7,
  "problems": [
    {
      "key": "api.unknown.key",
      "reason": "unknown_key",
      "reasonKey": "api.i18n.problem.unknown_key",
      "message": "La clave no existe en el catálogo de origen.",
      "params": {}
    }
  ]
}
```

A valid import returns `200` with `valid: true` and `applied: <changed rows>`;
importing the same content twice reports `applied: 0` and does not bump the
revision. Any problem makes the whole import fail: `422`, nothing is written
(valid rows included), and **every** problem is listed instead of stopping at
the first one. A failing import/validate returns the `422` error envelope with
`error.key = api.i18n.import_invalid` and `error.params = {"count": <n>}`, plus
the same `report` object at the top level.

Validation rules, by `reason` (each `reasonKey` is `api.i18n.problem.<reason>`):

| `reason` | Meaning |
|---|---|
| `unknown_key` | the key is not in the Spanish source catalog |
| `invalid_key` | the key does not follow the dotted catalog format |
| `namespace_not_allowed` | the source registration accepts only `ui.*` |
| `duplicate_key` | the catalog repeats a key (JSON pairs or two PO entries with the same `msgctxt`) |
| `empty_text` | the translation is empty or whitespace only |
| `too_long` | longer than the catalog message limit |
| `invalid_value` | a JSON value is not a string |
| `malformed_message` | unbalanced braces or an invalid `{parameter}` |
| `parameters_mismatch` | the placeholder set differs from the source (`params.missing`/`params.unexpected`) |
| `plural_forms_mismatch` | the pipe-separated form count differs from the CLDR categories of the locale (or from the source template when CLDR has more categories) |
| `invalid_json`, `invalid_po` | the content cannot be parsed |
| `unknown_locale`, `source_locale_missing`, `unknown_context`, `source_key_missing` | registration/coverage level problems |

Empty `msgstr` entries in a PO file are skipped ("not translated yet"); a PO
entry whose `msgstr` is a plural tuple is joined with ` | `. `msgctxt` is the
only key authority, so an entry without one is ignored.

### Delete

`DELETE /i18n/custom/{locale}/{key}` removes one custom translation and returns
`{"locale": "en", "deleted": 1, "revision": 8}`; an unknown key is `404`
`api.i18n.custom_key_not_found` with `params: {"locale", "key"}` and stores
nothing. `DELETE /i18n/custom/{locale}` resets the whole layer (also `200` with
`deleted: 0` when it was already empty). Both accept only installed locales
(`404` `api.i18n.unknown_locale`) and bump the revision once when a row is
actually removed.

### Custom translations and core upgrades

Custom translations live in `i18n_custom_translations` (main SQL), not in the
shipped `catalogs/*.json`, so installing a new core version never overwrites
them. They still win over the new owner text (: custom > pack override >
owner > pack fill), which is exactly what an upgrade must preserve. When a new
core version removes a key, the stored custom translation is kept but reported
as `custom.orphaned` in coverage (`reason: source_key_missing`, served nowhere)
instead of breaking the bundle. Revision `0042_i18n_custom` adds
`i18n_source_context`, the table that stores the translator context registered
with the frontend source catalog; it seeds no rows.

Audit: every accepted write records `i18n.sources_registered`,
`i18n.custom_imported` or `i18n.custom_deleted` with the resource
`i18n:source:ui` or `i18n:custom:<locale>`, in the same transaction as the rows
it describes. A rejected write records no success event.

## Language packs and extension catalogs

A language pack is an SDK package with `"kind": "language-pack"`; it installs
through the normal extension candidate → validation → approval flow but carries
no runtime code, storage or operations. Extension packages may instead declare
an optional `i18n` block that registers their own `ext.<id>.*` catalogs on
install and removes them on uninstall. See
`itsm/extensions/sdk/references/i18n.md` for the manifest blocks, compatibility
ranges, review status and examples (`sdk/examples/language-pack-pt-br`).

## Error envelope

```json
{"error": {"code": "validation_error", "message": "...", "key": "api.error.validation_error", "params": {}}}
```

`message` is localized for the request locale, including from a reviewed pack.
`key` and `params` are additive; a domain error without a key keeps its English
text as the legacy fallback (see "Domain error keys" for the converted modules).
Extension host refusals (`ExtensionHostError`) follow the same rule: each mapped
failure code has an `api.extensions.<code>` key and the host's own explanation
stays in `params.detail`, so no diagnostic text is lost to translation.
`422` responses also carry a top-level `details` list whose entries include `key`
(`api.validation.<pydantic error type>`, unknown types use `api.validation.invalid`),
`params` from the Pydantic `ctx` and a localized `message`.

## Domain error keys

Every user-visible `ValidationFailed`, `NotFound`, `Conflict`,
`PermissionDenied`, `AuthenticationFailed` and `BootstrapRefused` raised by a
converted module carries a stable key and named params:

```python
raise NotFound(
    f"{label} not found",                                    # unchanged English, for logs
    key="api.directory.record_not_found",
    params={"field": label},
)
```

- **Naming:** `api.<module>.<name>`, where `<module>` is the backend package
  (`identity`, `directory`, `maintenance`, `interventions`, `workflows`,
  `workspace`, `redundancy`, `ai_usage`, `appearance`, `attachments`, `system`,
  `search`, `events` in group A, plus `inventory`, `relationships`, `reports`,
  `dashboard`, `operations`, `monitoring`, `notifications`, `agent_integrations`,
  `agents`, `mcp` and `extensions` converted in ). Field-shape rules that repeat across
  modules reuse the shared `api.validation.*` keys instead of inventing one per
  module; the `api.<module>.record_not_found` key covers every resource lookup of
  a module with the resource label as `field`.
- **Message:** the first positional argument stays the existing English text so
  logs and any legacy consumer keep working; the HTTP layer renders `key` with
  the request locale and the additive `params` map.
- **Params:** only values are interpolated, never whole sentences. Field names,
  ids and enum values are technical identifiers and stay untranslated. A number
  that agrees with a noun also passes `count` and the catalog uses the
  `singular | plural` form (CLDR order); group A and messages phrase their
  bounded counts as fixed limits instead, so `count` is not used there yet.
- **Helpers first:** validation helpers that build messages from a label take
  the key and params once (`_text`, `_page_bounds`, `_row`, `_enum`), so each
  call site inherits them instead of repeating the key.
- **Enforcement:** `tests/test_i18n_error_keys.py` walks the AST of `itsm/` and
  fails when any module raises one of these classes without `key=`. No module is
  pending any more: closed the last one (`extensions`), so the allowlist is
  empty and may not grow again. The same suite
  asserts every key in code exists in `es`, `en` and `context.json` with
  exactly the parameter names the raise site passes, so a renamed param fails
  before it ships.

## Formatting

`itsm/i18n/formats.py` exposes `format_number`, `format_currency(value, locale,
currency)` and `format_datetime(value, locale, timezone)` for documents and
notifications. Pass the installation currency and time zone from the session
envelope; never hardcode them in a feature.

## Labels of admin-editable data

Categories, statuses, typed fields and relationship types keep a permanent
id/key. Their visible `label` (and a relationship type's `forwardLabel` /
`inverseLabel`) accepts either form:

- a plain string: legacy, kept valid, treated as source text;
- a locale map such as `{"es": "En mantenimiento", "en": "Under maintenance"}`
  with installed tags, non-empty text, at most 24 locales and at least the
  source locale (`es`).

`itsm/i18n/labels.py` owns the shared rule: `validate_label` normalizes a write,
`resolve_label` picks one text and `label_view` builds the public shape. Writes
accept `label` as a string or a map, and the explicit `labels` field; a read
payload echoes the text rendered for the request locale, so text that already
matches a mapped value is a no-op and any other text edits the source entry.
Invalid maps (unknown tag, empty text, missing source, too many locales) are
rejected with 422 and nothing is stored.

Reads resolve the request locale (`label`) and always expose the whole map
(`labels`, `{}` for a legacy string). Resolution follows the chain: requested
locale, its parents, the installation default, `es`, then the first available
text. Ids and keys never change with a language.

Fixed, non-editable state ids are not catalog rows; their text lives in
`itsm/i18n/catalogs/{es,en}.json` under `api.inventory.lifecycle.<id>`,
`api.interventions.state.<id>`, `api.interventions.type.<id>`,
`api.interventions.priority.<id>`, `api.maintenance.status.<id>` and
`api.maintenance.state.<id>`. Payloads expose them additively as
`statusLabel`, `typeLabel` and `priorityLabel` next to the unchanged id.

Built-in defaults ship `es` and `en` maps: `itsm/inventory/catalog_defaults.py`
for fresh installations and revision `0041_i18n_labels` for existing ones, which
backfills the English caption while keeping the stored Spanish text. The REST
adapters pass the request locale; agents, workers and CLI callers without one
fall back to the installation default locale instead of a hard-coded tag.

## Documents and notifications

`itsm/i18n/documents.py` keeps the two places that do not inherit the request
locale on one seam: a **document** uses the requested document locale (falling
back to the requester's preference and then the installation default) and a
**notification** uses each recipient's effective locale (`Identity.locale` ??
installation default). Locale, time zone and currency stay independent: choosing
`en` translates text but never turns `PYG` into `USD` or the installation zone
into anything else.

- Reports accept an optional `locale` on `POST /reports/preview` and
  `POST /reports/jobs`. It is validated against the installed tags (an instal-
  lation subtag resolves to its parent, so `en-US` → `en`), stored inside
  `ReportJob.request`, and reused when the worker renders asynchronously. An
  unknown tag is a `422` and stores nothing.
- Document text — titles, family and column labels, group and coverage names,
  `<html lang>`, page footer, summary facts and empty states — comes from
  `api.reports.*` keys (`itsm/reports/labels.py`). Dates, numbers and amounts are
  formatted with the document locale plus the installation time zone and
  currency. User free text (names, notes, branding) is never translated.
- A notification event stores `message = {"title": {"key", "params"}, "body":
  {"key", "params"}}` in the additive `notification_events.message` column
  (migration `0040_notification_i18n`). Fan-out renders it once per recipient, so
  the inbox row and every external Apprise/SMTP payload carry that recipient's
  language. External rows are queued per recipient instead of once per channel.
  Legacy events without a `message` keep their stored `title`/`body` verbatim.
- Operational results (`inventory_operation`, the operational summary tool)
  return a `message` object with `key`, `params`, `locale` and the rendered
  text.

## Agents

Agent surfaces keep their technical contract and vary only the language.

- **Tool names and schemas are stable.** MCP and Pydantic AI tool names,
  argument names and JSON schemas never change with locale. What may be
  localized is the human-readable description and the instructions.
- **Instructions per conversation locale.** `itsm/agents/locales.py` holds the
  `es` source prompt and its `en` translation. `AgentRuntime` resolves the
  locale for each turn (`chat`/`chat_with_usage` accept the trusted `locale`
  from the transport, never from the request body) and builds the agent for
  that instruction language; `IsolatedRuntime` forwards the same value. A
  request without a locale keeps the `es` source prompt.
- **Conversations keep their language.** `agent_sessions.locale`
  (migration `0043_conversation_locale`, ≤32 chars) stores the user's effective
  locale when the conversation is created. Later turns reuse the stored value,
  so changing the profile preference does not silently switch an ongoing
  conversation, and a tool result in another language never does either.
- **Tool descriptions are localizable by catalog.** `api.agents.tool.<toolName>`
  keys (`es`/`en`, with `context.json` entries) override the registered
  description for that tool. Tools without a key keep their registered
  description. Adding a translation never renames a tool or edits its schema.
- **MCP context carries the caller locale.** `itsm/mcp/server.py` appends
  `api.agents.locale.declared` — rendered for the negotiated locale — to the
  server instructions. The locale comes from the `Accept-Language` header of the
  session, negotiated against installed tags; tool names and input schemas stay
  byte-identical between locales.
- **`tools/list` descriptions follow the same locale.** Registration stays
  static: `LocaleContextMiddleware.on_list_tools` rewrites only the returned
  `description` of each tool from the `api.agents.tool.<toolName>` catalog for
  the negotiated request locale and leaves every other field (name, arguments,
  `inputSchema`) untouched. A tool without a catalog entry keeps its registered
  description.
- **External engines (Hermes/OpenCode) get the same context.** The integration
  service prepends one `system` history entry with the conversation locale
  before the engine prompt is composed (`itsm/agents/engines.py` renders it as
  system context, never as a user turn), so an external engine answers in the
  conversation language too.
- **Superadmin language-pack tools.** The SDK development boundary exposes four
  bounded methods through the same `system.modules` authority as the workspace
  tools (`DevelopmentService.dispatch`, so REST/agent/MCP transports share one
  implementation):

  | Tool | Arguments | Result |
  | --- | --- | --- |
  | `i18n_keys` | `namespace?`, `prefix?`, `limit?` (1–200, default 50), `offset?` | `total`, `limit`, `offset`, `keys[]` with `key`, `namespace`, `source`, `context`, `message` |
  | `i18n_missing` | `locale`, `namespace?`, `prefix?`, `limit?`, `offset?` | `locale`, `sourceLocale`, `chain`, `total`, `limit`, `offset`, `missing[]` |
  | `i18n_validate` | `locale`, `catalog` (object or JSON text), `overrides?` | `locale`, `valid`, `keys`, `errors[]` |
  | `i18n_package` | `workspace_id`, `locale`, `name?`, `native_name?`, `overrides?` | workspace payload, `id`, `tag`, `kind`, `review`, `compatibility`, `keys`, `manifest`, `files`, `message`, `next` |

  `i18n_keys` lists the source catalogs (core `es` plus every installed
  extension's own `ext.<id>.*` keys) with the translator context recorded in
  `context.json`. `i18n_missing` reports the keys the requested locale does not
  translate yet; the chain deliberately stops before the installation default so
  the Spanish fallback never hides a gap. `i18n_validate` reuses
  `itsm/i18n/packs.py` for key shape, parameters, plural forms and owner
  conflicts, and additionally checks the target locale's own Babel plural
  categories when they differ from the source. `i18n_package` scaffolds a
  language-pack workspace (`extension.json` plus `i18n/<tag>.json`) with
  `review.status: draft`, core compatibility derived from the running core
  version and one `^version` range per installed extension provider. It never
  marks a pack reviewed: AI-generated text stays reviewable and a human
  publishes it through `POST /api/v1/extensions/{id}/review`.

  `extension_workspace_validate` runs the same language-pack and
extension-catalog rules as approval (`itsm/i18n/packs.validate_i18n_files`, the
shared entry point behind `i18n_validate` and the host approval path), so a
pack with a wrong `{param}` or a missing extension translation fails validation
with the localized report instead of passing and failing only at approval. The
rules are never duplicated in the development service: it supplies the source
catalogs and owner catalogs and reuses `packs.py`.

### Existing UI message compatibility

Named placeholders accept ASCII letters and underscores initially, followed by
ASCII letters, digits or underscores. Names are case-sensitive and preserved,
including `cacheRead`, `noData`, `detectedAt` and `alertId`.

A complete, non-empty JSON object whose names and values are strings, parsed with
the standard JSON grammar (whitespace around tokens included), is literal example
text, not an interpolation template. Duplicate names, non-string names or values,
empty objects and trailing content are not literal text. For literal text,
parameter extraction returns no names, rendering preserves it unchanged, and it
counts as one plural form in source and translation comparison, so a `|` inside a
JSON string value never becomes a plural separator. Other brace-delimited text
