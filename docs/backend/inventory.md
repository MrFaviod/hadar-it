# Inventory slice and agent interfaces

Phase 3 delivered the first agent-first inventory slice: one canonical service
reused by the REST API, the Pydantic AI assistant and the FastMCP server. Phase 4
extends it with catalog-driven fields, lifecycle/history/media and configured
quick codes; see `docs/backend/asset-core.md`, `docs/backend/inventory-catalog.md` and
`docs/backend/inventory-identification.md`. This document describes the shared slice and
the transport contracts.

## Data model

Table `assets` (base migration `0003_inventory`, extended by the phase 4
revisions: `cost`, `technical`, `archived_at`, `archived_by`, history, media and
code counters - see `docs/backend/asset-core.md`):

| Field | Bound | Notes |
|---|---|---|
| `id` | UUID string (36) | Generated by the server, permanent and immutable |
| `quickCode` | 1-32, `[A-Za-z0-9][A-Za-z0-9._/-]*` | Editable, unique case-insensitively; a colliding numeric value advances its suffix, a suffixless duplicate is `409`; generated in the configured catalog format (`DC-SER-01`) or as `A-<8 hex>` when the category is unknown |
| `name` | 1-160 required | |
| `category`, `type`, `brand` | 1-64 | |
| `model`, `serial`, `ip` | 1-80 | |
| `site`, `location`, `responsible` | 1-120 | Legacy free-text labels; inventory people are not access accounts |
| `siteId`, `locationId`, `responsiblePersonId` | UUID string (36), nullable | Canonical directory references; ids are the authority and the legacy text above mirrors their current label on read (`docs/backend/asset-organization.md`). An explicit `null` clears the reference and its text; clearing or switching the site also drops the stored location and position unless a replacement `locationId` is sent |
| `positionX`, `positionY` | `0..1`, 6 decimals, nullable | Optional relative plan position, only with a `locationId` |
| `status` | catalog status ids | Defaults to `in_use`; active catalog statuses and transitions apply (`docs/backend/inventory-catalog.md`) |
| `description` | 1-1000 | |
| `createdAt`, `updatedAt` | server clock | UTC, ISO-8601 in payloads |

`quickCode` normalization lowercases the stored key used for uniqueness while
the visible value keeps the caller's casing. Allocation follows the configured
identification rule and holds a serialized transaction lock; see
`docs/backend/inventory-identification.md`. Sending `id` in an update or batch
update is rejected (`422`); sending an unknown field is rejected at every door.
The stable API vocabulary uses `in_use`; the UI may label it in Spanish.

## Service

`itsm/inventory/service.py` (`InventoryService`) owns validation, Casbin
authorization, SQL and audit for every front door:

- `search` requires `assets.view`; filters `query`, `category`, `site`,
  `status`, `quickCode` and `id`; `query` searches name, quickCode, serial,
  brand, model, responsible and ip with escaped `LIKE` wildcards; pagination is
  bounded (`limit` 1-200, `offset >= 0`) and ordered by `updatedAt desc, id`.
  Filtering by a missing, purged or malformed string asset id returns an empty
  page, preserving the requested limit/offset; non-string ids are invalid.
  Global `assets.view` authorization still precedes search and does not provide
  per-asset visibility filtering. `get` continues to raise `NotFound` for a
  missing or purged id.
- `get` requires `assets.view`. `site`, `location` and `responsible` are
derived from the current directory rows of an id-backed asset, so a directory
rename changes what a read reports without touching the asset or its history.
- `create` requires `assets.edit`, plus `assets.assign` when a `responsible` is
  supplied. The generated `id` is returned and never changes.
- `update` requires `assets.edit`, plus `assets.assign` when `responsible`
  changes. Updates are partial; `None` clears an optional field, and for a
  reference/text pair it clears both halves together.
- `batch` accepts at most 50 creates and/or updates (each update keyed by `id`),
  authorizes every item before writing, rejects suffixless quick codes repeated
  inside the same request and commits once: a failure leaves no partial rows.
- A suffixless duplicate quick code surfaces as `409`; a numeric collision
  advances the suffix instead. Unknown ids are `404`; invalid or extra
  input is `422`. Every allowed write records `inventory.asset_created`,
  `inventory.asset_updated`, `inventory.assets_batch_created` or
  `inventory.assets_batch_updated`; denials are audited by `IdentityService`.
- Search goes through `InventorySearch`-shaped service methods only; a future
  Meilisearch adapter can replace the SQL implementation without changing API,
  agent or MCP contracts. Its absence never blocks inventory search.

## REST API

All routes use `ITSM_API_PREFIX` (default `/api/v1`) and the shared error
envelope.

- `GET /assets` and `GET /assets/search` — same bounded envelope
  `{items, total, limit, offset}`; query parameters `query`, `category`, `site`,
  `status`, `quickCode`, `id`, `limit`, `offset`.
- `GET /assets/{id}` — one asset or `404`.
- `POST /assets` — `201` with the created asset; extra fields rejected.
- `PATCH /assets/{id}` — partial update; `422` for immutable/unknown fields.
- `POST /assets/batch` — `{create: [...], update: [{id, ...}]}`, at most 50 each,
  atomic, returns `{created: [...], updated: [...]}`.

Reads need `assets.view`; writes need `assets.edit` and `assets.assign` for
responsible changes. Browser sessions require `Origin` plus `X-CSRF-Token`;
machine bearers are exempt from CSRF but still authorized through Casbin.

## Conversational agent

`POST /api/v1/agent/chat` (cookie or bearer) accepts:

```json
{"message": "Mostrame los switches de Sede Norte", "conversation": [{"role": "user", "content": "..."}], "assetId": "uuid"}
```

- `conversation` accepts only `user`/`assistant` text turns; `system`/`tool`
  roles, extra fields (for example a caller-supplied model) and over-long input
  are rejected.
- The reply is compact:
  `{"message": str, "actions": [{"tool", "status": "completed|failed|denied", "assetIds"}], "results": [...], "approvalPending": false}`.
  `approvalPending` is always `false` while no dangerous-operation approval
  framework exists.
- Tools: `search_assets`, `get_asset`, `create_asset`, `update_asset`,
  `batch_update_assets`, `clone_asset`, `archive_asset`, `restore_asset`,
  `retire_asset`, `get_asset_history`, `get_inventory_config`. Each tool reuses
  `InventoryService`, so it applies the same permissions and audit. There is no
  shell, SQL, filesystem or HTTP tool, and the model cannot introduce one from
  conversation text. Outputs are compact asset summaries with an optional
  `fields` projection (`docs/backend/inventory-identification.md`).
- Missing asset/field data must be requested from the person, never invented;
  the instructions tell the model to ask instead of guessing.
- Provider/model come only from server configuration. If it is not configured
  the endpoint returns `503 unavailable`; it never falls back to a fake or
  simulated model in production. Tool-call steps, request limits, history and
  output tokens are bounded by settings.

Configuration (process environment, no `.env` file):

| Variable | Default | Purpose |
|---|---|---|
| `ITSM_AGENT_MODEL` | empty | `openai:<model>` or `anthropic:<model>`; empty disables chat with `503` |
| `ITSM_AGENT_MAX_STEPS` | `8` | Request/tool loop bound (1-16) |
| `ITSM_AGENT_MAX_HISTORY_MESSAGES` | `20` | Accepted conversation turns (0-50) |
| `ITSM_AGENT_MAX_OUTPUT_TOKENS` | `1024` | Output token ceiling (64-4096) |
| `ITSM_AGENT_MESSAGE_MAX_LENGTH` | `4000` | Per-message input bound (1-8000) |
| `ITSM_AGENT_OPENAI_BASE_URL` | empty | Optional OpenAI-compatible base URL, server-side only |

Provider credentials come from the SDK-standard environment variables
(`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`); they are never
modeled as `ITSM_` settings, never accepted from a request and are covered by
log redaction together with URL credentials.

Deterministic tests use Pydantic AI `FunctionModel` and
`ALLOW_MODEL_REQUESTS=False`; no provider inference is consumed.

## MCP server

FastMCP (standalone `fastmcp` package) is mounted in the existing FastAPI app at
`{api_prefix}/mcp` using the Streamable HTTP transport. Its lifespan is entered
from the application lifespan; no second server process is needed.

- Bearer-only. The raw `Authorization` header is re-read from the trusted
  transport for the request and again for every tool call; cookie sessions are
  rejected and a revoked token, deactivated identity or invalid token fails
  immediately, with no cached principal and no actor/scope/permission taken from
  tool arguments.
- Selected tools only: the same twenty-one typed tools the assistant uses - the
  eleven inventory tools (search, get, create, update, batch update, clone,
  archive, restore, retire, asset history and inventory config) plus
  `search_locations`, `search_people`, `assign_asset`, `return_asset`,
  `transfer_asset`, `get_asset_relations`, `create_relationship`,
  `remove_relationship`, `move_host` and `get_asset_map`. The REST surface is
  not exported automatically; see `docs/backend/asset-organization.md`.
- Tool outputs are compact camelCase asset summaries with the optional `fields`
  projection; errors use safe messages.
- Scopes reported by the verifier are the identity's effective permissions, so
  the same Casbin policy governs REST, agent and MCP mutations.

Example client (Hermes or any MCP-compatible client):

```python
from fastmcp import Client
from fastmcp.client.transports import StreamableHttpTransport

transport = StreamableHttpTransport(
    "http://127.0.0.1:8000/api/v1/mcp",
    headers={"Authorization": "Bearer <machine-token>"},
)
async with Client(transport) as client:
    print(await client.list_tools())
    print(await client.call_tool("search_assets", {"query": "Aruba"}))
```

## Verification limits

Covered by tests: service-level validation/authorization/audit, REST contract,
cookie CSRF and machine identity failures, atomic batches, SQL wildcard and
injection-shaped queries, deterministic agent tool chains, actual MCP protocol
client calls, revocation, and cross-interface identity/parity.

Not covered: external engine matrices (SQLite only), real provider inference,
Meilisearch/Redis/Huey for basic CRUD, approval workflows and a destructive
purge UX. Typed relationships, canonical organization references, structured
history and map queries are covered; the graph endpoint may omit an edge
endpoint because of the node budget, which consumers must handle explicitly.
This is not a general security certification.
