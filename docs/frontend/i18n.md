# Frontend internationalization (`ui.*`)

Scope: the frontend runtime and the shell surfaces it localizes. Screen copy
outside the shell is still Spanish and is being swept separately; do not treat
this document as a statement of coverage.

## Runtime

- `assets/vendor/vue-i18n.global.prod.js` (vue-i18n 11.4.17, MIT) is vendored and
  loaded right after Vue. `assets/js/i18n.js` is the only glue: it creates the
  single instance, loads catalogs, merges the server overlay, formats values and
  reports missing keys.
- Templates use `$t`, `$n` and `$d`. Plain modules call the runtime:
  `window.ItsmI18n.t(key, params)`, plus `number`, `amount`, `date`, `datetime`,
  `time`, `formatDate`, `collator` and `compare`.
- Inline templates are string templates, so `$t` works in `index.html` and in
  component `template` strings without extra registration.

## Catalogs

| File | Content |
|---|---|
| `assets/i18n/es.json` | Source catalog. Spanish is the source locale and uses the `tú` convention. |
| `assets/i18n/en.json` | English catalog. Same keys and same parameter names as `es.json`. |
| `assets/i18n/context.json` | One short usage description per key. |

Flat dotted keys (`"ui.shell.logout": "Cerrar sesión"`), named parameters
(`"Reinicio en {time}"`), and plural forms separated by ` | ` in CLDR category
order (`zero | one | two | few | many | other`, categories restricted per locale).
`count` selects the form through `Intl.PluralRules`.

`tests/i18n-catalogs.test.cjs` enforces key parity, parameter parity, plural-form
parity, context coverage, and that every literal key used by
`$t('…')`/`ItsmI18n.t('…')` in `index.html` and `assets/js/*.js` exists in `es`.

## Adding a key

1. Add the entry to `es.json` (source) and `en.json`, in the same position, with
   identical `{params}` and plural-form count.
2. Add a one-line description to `context.json`.
3. Use it through `$t('ui.…')` or `ItsmI18n.t('ui.…')`. Never build a key at
   runtime: the scanner only sees literals.
4. Run `npm test`.

## Server overlay and fallback

Built-in catalogs are the frontend `ui.*` core. The server bundle
(`GET /api/v1/i18n/bundle?locale=`) resolves as
`{ ...messages, ...builtinUi[locale], ...overrides }`, so an owner catalog entry
beats a fill-only pack entry and an explicit override beats both. Bundles are
cached by `ETag`. The fallback chain is requested locale → parent (`pt-BR` → `pt`)
→ installation default → `es`.

A key is never rendered: an unresolved key produces the localized
`ui.i18n.text_unavailable` string and is recorded in `ItsmI18n.misses`.

## Language selection

- Login screen, demo notice and the user menu render the same `<locale-select>`
  control (native `select` inside its own label).
- Before authenticating, the choice is stored in `localStorage['itsm.locale']`
  as a preference, not as authority.
- When signed in, the root saves the choice through
  `PATCH /api/v1/auth/me/preferences` with the existing CSRF/Origin client and
  applies the returned session envelope.
- Effective locale: user preference → anonymous selection → installation
  default. Switching language updates the UI in place: no reload, no route
  change, no remount, and component state (forms, selection, conversation) is
  preserved.
- Every API request sends `Accept-Language: <active locale>`, and `<html lang>`
  follows the active locale.

## Formats

Language, timezone and currency are independent (they come from the installation
settings, defaulting to `America/Asuncion` and `PYG`). English never changes
guaraníes to dollars and never changes the company timezone. Amounts are never
converted, only formatted.

Internal identifiers stay stable across languages: quick-code prefixes and slug
normalization keep their `es` case folding and accent stripping, because they are
identifiers, not display copy. Same for the search normalization paths.

## Errors

Envelope `{ error: { code, message, key?, params? } }`:

- `key` present → show the backend `message` (already localized by the server).
- no `key` → map `code` through `ui.errors.*`; an untranslated
  `validation_error` keeps its composed reason and field hints.

## Literal scanner

`tests/i18n-literals-scanner.cjs` counts human-visible hard-coded text in
`index.html` text nodes and `placeholder`/`title`/`aria-label`/`alt` attributes,
and in `template:` strings of `assets/js/*.js`.
`tests/i18n-literals-baseline.json` records the current count per file, and
`tests/i18n-literals.test.cjs` fails when a file goes **up**. Localized regions
must drop to zero. Regenerate deliberately with
`node tests/i18n-literals-baseline.cjs` only after a localization unit is done.

## Translator tools (`#/configuracion/idiomas`)

`assets/js/translation-views.js` (`TranslationSettings`) is the translator page.
It reads the translator scope and never invents authority:

- **Source registration.** On mount, and again when the shipped catalogs change,
  an account with `system.configure` registers the `ui` source through
  `PUT /api/v1/i18n/sources/ui` with the built-in `es`/`en` catalogs and
  `assets/i18n/context.json`. The write is idempotent by content, so a remount
  in the same page session does not repeat it.
- **Coverage.** `GET /api/v1/i18n/coverage` fills one table row per installed
  locale: name, native name, providers (`core`, `ui-source`, `extension`,
  `language-pack`, `custom`), translated/total, percentage formatted with
  `ItsmI18n.number`, and the orphaned custom count. The namespace filter sends
  `namespace=api|ui|ext.<id>`.
- **Missing keys.** A second, paged coverage read (`limit`, `offset`) lists the
  keys of the chosen locale with their registered context; the range comes from
  the returned page, never from an assumption about page size.
- **Export.** `GET /api/v1/i18n/export` with `locale`, `format` (`json`/`po`) and
  an optional namespace, downloaded through the blob branch of
  `AssetAccess.request`.
- **Validate and import.** `POST /api/v1/i18n/validate` writes nothing and shows
  the server report; `POST /api/v1/i18n/import` stores into the custom layer.
  Both show every `problems[]` entry using the server's localized `message`,
  falling back to `reasonKey` and then `reason`. After a successful import (or
  delete/reset) the page reloads coverage and the affected bundle through
  `ItsmI18n.loadBundle` / `ItsmI18n.setLocale`, so overrides appear without a
  page reload.
- **Custom layer.** The page lists the custom entries per locale, deletes one
  orphaned key or resets a whole locale behind an explicit confirmation. Both
  writes are `system.configure`; the shared custom layer is why a core update
  never removes a custom translation.

Reads need `system.view`, writes need `system.configure`; a reader keeps coverage,
validation and export and never sees an import, delete or reset action. The
server re-authorizes every write and records it in the audit trail.
`tests/translation-views.test.cjs` drives the mounted component against the
documented endpoints in both locales.
